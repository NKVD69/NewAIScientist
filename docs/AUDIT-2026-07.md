# NewAIScientist — Audit de la base de code et propositions d'améliorations profondes

*Analyse du dépôt `NKVD69/NewAIScientist` @ main — ~15 000 lignes Python, 68 modules, 17 fichiers de tests.*

---

## 0. Résumé exécutif

Le code est **bien meilleur que la moyenne** pour ce type de projet : typage moderne (`from __future__ import annotations`, `X | None`), dégradation gracieuse systématique des dépendances optionnelles, retry avec backoff exponentiel et jitter classifiant correctement les erreurs transitoires vs permanentes, helpers de sécurité API propres (path traversal, CORS sans wildcard), CI avec ruff + mypy + pytest.

Le problème n'est donc pas la qualité d'écriture. Il est ailleurs, et il est structurel. Trois constats se dégagent :

1. **Les composants les plus sophistiqués ne sont jamais appelés.** Le système contient une couche épistémique remarquable (`Claim`, `Evidence`, `Prediction.is_refuted_by()`) et un pipeline de retrieval hybride complet (BM25 + RRF + cross-encoder) — les deux sont du **code mort en production**, testés mais jamais câblés à l'orchestrateur.
2. **La boucle de validation empirique est circulaire.** Ce que le système appelle « expérience » consiste, dans le cas dominant, à demander à un LLM de générer des données synthétiques puis de conclure si elles supportent l'hypothèse qu'il a lui-même produite. Zéro information empirique entre.
3. **Le seul signal de sélection (Elo) est mal identifié et biaisé.** Position bias non corrigé, ~1,7 partie par hypothèse là où il en faudrait ~53, et une pression de sélection qui joue **contre** les hypothèses évoluées.

Les sections suivantes détaillent chaque point avec le code fautif, une démonstration lorsque c'est possible, et une correction proposée.

## 1. Le thème central : capacité implémentée ≠ capacité câblée

### 1.1 La couche `Claim` / `Evidence` est morte

`models/hypothesis.py` définit une modélisation épistémique de bonne facture :

```python
@dataclass
class Evidence:
    source_type: str = "prior"   # "rag" | "citation" | "prior" | "experiment"
    source_ref: str = ""         # DOI / arXiv ID / chunk ID
    polarity: int = 1            # +1 supporte, -1 contredit, 0 contextuel
    confidence: float = 0.5

@dataclass
class Claim:
    statement: str = ""
    evidence: list[Evidence] = field(default_factory=list)
    def evidence_score(self) -> float: ...   # agrégat pondéré dans [-1, 1]
```

Vérification par grep sur l'ensemble du code hors `tests/` et `models/` : **`Claim` et `Evidence` ne sont instanciés nulle part**. `evidence_score()` n'est jamais appelé. Le champ `Hypothesis.claims` n'existe même pas.

Conséquence concrète : une hypothèse est un blob de texte libre (`description`, `mechanism`, `testable_predictions: list[str]`). Il est donc **impossible** de réfuter partiellement une hypothèse, de tracer quelle preuve soutient quelle affirmation, ou de détecter qu'une hypothèse évoluée a discrètement abandonné l'affirmation centrale de son parent.

### 1.2 Le retrieval hybride est mort

`utils/hybrid_retrieval.py` (277 lignes) implémente proprement BM25 → RRF → cross-encoder rerank, et `rag_system.py` expose `RAGEngine.query_hybrid()`. Or :

```
$ grep -rn "query_hybrid" --include="*.py" . | grep -v tests/
./rag_system.py:773:    async def query_hybrid(   # ← définition seulement
```

Tous les chemins de production passent par `RAGEngine.query()` — **dense uniquement**, avec `all-MiniLM-L6-v2`. Le module hybride existe, est testé (205 lignes de tests), et n'est jamais utilisé.

### 1.3 Correction

Ce n'est pas un problème de refactoring, c'est un problème de contrat entre couches. Proposition : imposer que **toute nouvelle capacité soit accompagnée d'un test d'intégration qui l'exerce depuis `CoScientist`**, pas seulement d'un test unitaire. Un test comme :

```python
async def test_generation_produces_structured_claims():
    hyps = await co.run_hypothesis_generation_cycle(num_hypotheses=2)
    assert all(h.claims for h in hyps)               # échoue aujourd'hui
    assert all(c.evidence for h in hyps for c in h.claims)
```

aurait empêché la dérive. Et à court terme : brancher `query_hybrid` (une ligne dans `literature.py:456`) et faire produire des `Claim` par le `GenerationAgent`.

## 2. Failles épistémiques (le cœur du sujet)

### 2.1 La boucle de réfutation est un `grep`

`co_scientist.py:376`, dans `run_revision_cycle()` :

```python
lower_results = hyp.experimental_results.lower()
if "fail" in lower_results or "not support" in lower_results \
   or "refute" in lower_results or "reject" in lower_results:
    refuted = True
```

C'est de la détection de réfutation par sous-chaîne sur la sortie stdout d'un script. Les modes d'échec sont immédiats :

- **Faux positif massif** : `"failed to reject the null hypothesis"` — la formule statistique standard signifiant *l'absence de preuve contre* — contient `"fail"` **et** `"reject"`. Le système la lit comme une réfutation.
- **Faux négatif** : `"the data did not support the prediction"` passe (contient `"not support"`), mais `"observed IC50 = 47 µM vs predicted 2 µM"` — une réfutation nette et quantitative — ne déclenche rien.
- Aucune granularité : une hypothèse à cinq prédictions est réfutée en bloc ou pas du tout.

Le plus frustrant est que **la machinerie correcte existe déjà** :

```python
# models/hypothesis.py
def is_refuted_by(self, observed: float) -> bool:
    if not self.is_falsifiable():
        return False
    return abs(observed - self.expected_value) > self.refuting_threshold
```

`is_refuted_by` n'est appelé nulle part. Le `PreregistrationAgent` produit consciencieusement des `Prediction` avec `expected_value`, `ci`, `unit`, `refuting_threshold`… puis personne ne les confronte jamais aux résultats.

**Correction proposée** — fermer réellement la boucle :

```python
# agents/experiment.py — le script généré doit émettre du structuré
PROMPT_SUFFIX = """
Terminate your script with exactly one line of the form:
RESULTS_JSON: {"measurements": [{"quantity": "<nom>", "observed": <float>,
               "unit": "<unité>", "ci_low": <float>, "ci_high": <float>,
               "n": <int>, "test": "<nom du test>", "p": <float>}]}
"""

# nouveau module utils/adjudication.py
def adjudicate(hyp: Hypothesis, measurements: list[dict]) -> list[Verdict]:
    """Confronte chaque Prediction préenregistrée à sa mesure observée."""
    by_quantity = {m["quantity"].lower(): m for m in measurements}
    verdicts = []
    for pred in hyp.falsifiable_predictions:
        obs = by_quantity.get(pred.quantity.lower())
        if obs is None:
            verdicts.append(Verdict(pred, status="untested",
                                    reason="aucune mesure correspondante"))
            continue
        if not pred.is_falsifiable():
            verdicts.append(Verdict(pred, status="unfalsifiable"))
            continue
        # Unités : refuser plutôt que comparer des pommes et des oranges
        if not units_compatible(pred.unit, obs["unit"]):
            verdicts.append(Verdict(pred, status="invalid",
                                    reason=f"unité {obs['unit']} ≠ {pred.unit}"))
            continue
        refuted = pred.is_refuted_by(obs["observed"])
        verdicts.append(Verdict(pred, status="refuted" if refuted else "corroborated",
                                observed=obs["observed"]))
    return verdicts
```

`run_revision_cycle` déclenche alors une révision **par prédiction réfutée**, en passant à `EvolutionAgent` le détail (quantité, attendu, observé) plutôt qu'un blob de texte. Et une hypothèse dont toutes les prédictions sont `untested` doit être marquée comme telle — pas silencieusement traitée comme corroborée, ce qui est le comportement actuel.

### 2.2 « L'expérience » est circulaire

`agents/experiment.py` a deux chemins :

**Chemin A — aucun médicament détecté dans le texte** (le cas par défaut pour toute hypothèse non pharmacologique) :

```python
data_description = (
    "No real data file is available. Generate realistic synthetic data "
    "based on known pharmacological properties for the hypothesis."
)
```

Le LLM génère des données, applique des t-tests dessus, et conclut si « les données supportent l'hypothèse ». Les p-valeurs produites mesurent la cohérence interne du générateur avec lui-même. Ce n'est pas une validation empirique faible : c'est zéro bit d'information externe, présenté avec l'appareil rhétorique complet (effect sizes, intervalles de confiance) d'une validation. C'est le mode de défaillance le plus dangereux du système, parce que la sortie est **indiscernable** d'un vrai résultat en aval — le `WritingAgent` la rédigera en Results.

**Chemin B — des médicaments sont détectés** : le système récupère de PubChem `MolecularWeight, XLogP, HBondDonorCount, HBondAcceptorCount, TPSA`. Ce sont des descripteurs physicochimiques. L'objectif de recherche par défaut du dépôt est *« identifier des médicaments repositionnables inhibant la prolifération des cellules AML sur lignée MOLM-13 »*. Corréler le TPSA avec une hypothèse d'inhibition de prolifération leucémique n'est pas un test de cette hypothèse — c'est un test de descripteurs de Lipinski. Les données sont réelles ; leur pertinence pour la question posée est nulle.

**Correction proposée** — typer les expériences et refuser explicitement :

```python
class ExperimentKind(Enum):
    DRY_RUN_SIMULATION = "simulation"      # ⚠ synthétique, ne peut PAS corroborer
    REAL_DATA_ANALYSIS = "real_data"       # source externe vérifiable
    LITERATURE_META    = "literature_meta" # effets extraits de publications
    INFEASIBLE         = "infeasible"      # aucune donnée accessible

# Règle dure, appliquée dans adjudicate()
if experiment.kind is ExperimentKind.DRY_RUN_SIMULATION:
    # une simulation peut RÉFUTER (incohérence interne, contradiction
    # mathématique) mais ne peut jamais CORROBORER
    verdicts = [v for v in verdicts if v.status == "refuted"]
```

Et surtout, ouvrir des connecteurs vers des sources où l'hypothèse est réellement testable :

| Source | Ce qu'elle apporte | API |
|---|---|---|
| **ChEMBL** | bioactivités mesurées (IC50, Ki) composé × cible | REST publique |
| **DepMap** | dépendances géniques CRISPR par lignée cellulaire | fichiers + API |
| **LINCS L1000** | signatures transcriptionnelles post-perturbation | clue.io |
| **Open Targets** | associations cible–maladie avec scores de preuve | GraphQL |
| **GEO / ArrayExpress** | données d'expression brutes réanalysables | E-utilities |

Pour l'objectif AML par défaut, DepMap + ChEMBL permettraient un test réel : *ce composé touche-t-il une cible dont MOLM-13 est effectivement dépendante ?* C'est un changement de nature, pas de degré.

### 2.3 La « réplication » ne réplique rien

`agents/replication.py` re-exécute le script en injectant des seeds différents :

```python
f"np.random.seed({seed})\n"
f"random.seed({seed})\n"
```

Deux cas, tous deux vides de sens :

- Données réelles (PubChem/CSV) → l'analyse est déterministe, la variance entre seeds est **nulle par construction**. Le système rapportera une reproductibilité parfaite, ce qui est vrai et sans intérêt.
- Données synthétiques → on mesure la variance du générateur pseudo-aléatoire. Un résultat « robuste » signifie simplement que le LLM a écrit un `np.random.normal` avec un écart-type petit.

Dans les deux cas, la métrique de reproductibilité affichée est trompeuse.

**Correction proposée** : remplacer la variation de seed par une **analyse multivers** (*specification curve*), qui est la vraie question de reproductibilité :

```python
SPECIFICATIONS = {
    "outlier_policy":   ["none", "iqr_1.5", "winsorize_5pct"],
    "test":             ["welch_t", "mann_whitney", "permutation"],
    "transform":        ["identity", "log", "rank"],
    "covariate_adjust": [True, False],
}
# 3 × 3 × 3 × 2 = 54 spécifications défendables
# Rapporter la distribution des effets, pas un point.
# Fragilité = fraction des spécifications qui inversent la conclusion.
```

Une hypothèse qui ne survit qu'à 4 spécifications sur 54 doit être pénalisée dans le classement. C'est un signal réel, calculable, et actuellement absent.

### 2.4 La nouveauté n'est jamais vérifiée contre la littérature

C'est le critère le mieux pondéré du système (0,25 dans `RankingAgent.DEFAULT_CRITERIA_WEIGHTS`, et il pilote `novelty_level` puis les bonus Elo). Or il n'est jamais mesuré.

Chemin LLM : le méta-reviewer renvoie un `novelty_score` par introspection, **sans aucune recherche d'antériorité**. Le modèle juge la nouveauté d'après sa mémoire paramétrique, pour un domaine où il est le plus faible (publications récentes, littérature de niche).

Chemin fallback, `agents/reflection.py:_assess_novelty` :

```python
score = 0.6
if "simulated" in hypothesis.generation_method:  score = 0.55
elif "llm" in hypothesis.generation_method:      score = 0.75
elif hypothesis.generation_method == "evolved":  score = 0.65
```

La nouveauté est ici une **fonction du mode de génération**. Une hypothèse est jugée 36 % plus novatrice parce qu'elle a été produite par un LLM plutôt que par le stub de simulation. C'est un artefact de plomberie promu au rang de mesure scientifique, et il se propage jusqu'à l'Elo puis au manuscrit final.

**Correction proposée** — une nouveauté triangulée et vérifiable :

```python
async def measure_novelty(hyp, rag_engine, literature_agent) -> NoveltyReport:
    # 1. Distance au corpus indexé (dense + BM25 via query_hybrid)
    neighbours = await rag_engine.query_hybrid(hyp.statement_text(), top_k=20)
    max_sim = max(n["score"] for n in neighbours) if neighbours else 0.0

    # 2. Recherche d'antériorité ciblée : requête construite à partir des
    #    entités + relation revendiquées, pas du titre
    prior_art = await literature_agent.search_prior_art(
        entities=hyp.entities, relation=hyp.claimed_relation)

    # 3. Nouveauté de l'arête dans le graphe de connaissances
    edge_exists = graph_agent.has_edge(hyp.subject, hyp.predicate, hyp.object)

    return NoveltyReport(
        corpus_distance=1.0 - max_sim,
        prior_art_hits=prior_art,          # ← auditable par le scientifique
        edge_is_new=not edge_exists,
        nearest_papers=neighbours[:3],     # ← « voici ce qui existe déjà »
    )
```

Le point important n'est pas le score : c'est que le rapport soit **auditable**. Un chercheur doit pouvoir voir les trois articles les plus proches et juger lui-même. Un scalaire opaque de 0,75 ne vaut rien.

### 2.5 La vérification d'intégrité du préenregistrement est vide (bug démontré)

`agents/preregistration.py` :

```python
bundle = {
    "timestamp": datetime.now().isoformat(),   # ← dans le hash
    "predictions": [...],
}
return hashlib.sha256(json.dumps(bundle, sort_keys=True).encode()).hexdigest()
```

Et plus bas, dans `verify_integrity`, avec une docstring qui affirme le contraire de ce que fait le code :

```python
# We only compare the prediction content, not the timestamp
# (which differs between registration and verification)
return current_hash == hypothesis.prediction_hash
```

Le timestamp *est* dans le bundle haché. Vérification empirique :

```
hash1: a4588a193804eacd589b33d2
hash2: 852aff2465715122ef571f31   (mêmes prédictions, 1,1 s plus tard)
IDENTICAL? False
```

**`verify_integrity()` retourne systématiquement `False`.** La garantie anti-HARKing du système — sa fonctionnalité la plus mise en avant côté rigueur — ne fonctionne pas. Correction : sortir le timestamp du bundle et le stocker à côté du hash.

## 3. Le classement Elo : unique signal de sélection, et il est cassé

Tout converge vers l'Elo : sélection des hypothèses à évoluer (top-3), à expérimenter (top-2), à répliquer (top-2), à protocoler (top-1), et l'hypothèse dont le manuscrit final est rédigé (top-1). Les scores de revue (`correctness`, `testability`, `quality`) n'alimentent **rien** hors du fallback heuristique. Un signal unique, donc — il a intérêt à être bon.

### 3.1 Biais de position non corrigé

```python
f"Hypothesis A (ID: {hyp_a.id}):\n" ...
f"Hypothesis B (ID: {hyp_b.id}):\n" ...
```

`hyp_a` est **toujours** en position A. Le biais de position des LLM-as-judge est important et bien documenté ; ici il n'est ni randomisé ni compensé. Aggravation dans l'agrégation :

```python
# Tie ⇒ pick A deterministically (first listed).
return a_id if score_a >= score_b else b_id
```

Or `pair_plan` est construit par `information_gain_pairing`, dont l'ordre des tuples n'est pas aléatoire — le biais est donc **systématique**, pas moyenné.

**Correction** : double passage (A/B puis B/A) avec position permutée, et n'accepter le verdict que s'il est cohérent ; sinon match nul. Coût : ×2 en appels, mais c'est le signal le plus critique du système.

```python
v1 = await self._multi_judge(hyp_a, hyp_b)     # A en premier
v2 = await self._multi_judge(hyp_b, hyp_a)     # B en premier
consistent = {c: v1[c] for c in v1 if v1.get(c) == v2.get(c)}
# critères incohérents ⇒ nul (0.5), pas de gain Elo
```

### 3.2 Elo massivement sous-échantillonné

Avec les paramètres par défaut (`num_hypotheses=5`, `iterations=3`, 3 évolutions/itération, `num_matches=4`) :

```
hypothèses finales : 14
matchs joués       : 12
parties/hypothèse  : 1.71
nécessaire (~n·log₂n) : 53 matchs
```

**1,7 partie par hypothèse.** L'Elo n'est pas identifié : la plupart des hypothèses conservent une note proche de 1200 ± bruit, et le top-1 qui décide du manuscrit est essentiellement tiré au sort parmi celles qui ont eu la chance de jouer. Pire, le pool grandit (5 → 8 → 11 → 14) alors que `num_matches` reste constant à 4.

### 3.3 Pression de sélection contre l'évolution (anti-darwinien)

`Hypothesis.elo_rating` par défaut = 1200,0. `EvolutionAgent.evolve_hypothesis` crée un nouvel objet sans héritage :

```python
new_hyp = Hypothesis(..., parent_ids=[hypothesis.id], generation_method="evolved")
# elo_rating = 1200.0 par défaut
```

Les parents sélectionnés pour évoluer sont, par définition, les **top-3 par Elo** — donc à 1250-1300. Leurs descendants naissent à 1200, donc **en dessous**, et avec ~1,7 partie pour remonter, ils n'y parviennent pas. Le tournoi sélectionne donc préférentiellement les hypothèses de la génération initiale. La boucle évolutionnaire tourne mais ne peut pas produire de gain sélectif : c'est exactement l'inverse du mécanisme recherché.

### 3.4 Correction d'ensemble du classement

```python
# 1. Héritage avec pénalité de régression vers la moyenne
new_hyp.elo_rating = 1200.0 + 0.7 * (parent.elo_rating - 1200.0)

# 2. Passer d'Elo à un modèle avec incertitude explicite (TrueSkill / Bradley-Terry)
#    μ ET σ. On n'arrête le tournoi que quand le top-1 est séparé du top-2
#    de plus de 2σ. Sinon, on continue à jouer.
def tournament_budget(n: int) -> int:
    return max(8, int(2 * n * math.log2(max(2, n))))   # 14 hyp → 106 matchs

# 3. Intégrer les signaux orphelins dans le prior, au lieu de les ignorer
prior = (0.35 * review.correctness_score
       + 0.25 * novelty_report.corpus_distance     # nouveauté mesurée, §2.4
       + 0.25 * falsifiability_score               # déjà calculé, jamais utilisé
       + 0.15 * (1.0 - multiverse_fragility))      # §2.3
mu_initial = 1200.0 + 400.0 * (prior - 0.5)
```

Point 3 : `falsifiability_score` est calculé par le `PreregistrationAgent` et n'influence rien. Idem pour tous les scores de revue. Le système produit une riche information d'évaluation qu'il jette ensuite.

## 4. Sécurité de l'exécution : le filtre AST est contournable de dix façons

`utils/safety.py` n'inspecte que les nœuds `ast.Import` et `ast.ImportFrom` contre une liste noire de 17 modules. Test empirique exécuté sur le code du dépôt :

| Technique | Verdict du filtre |
|---|---|
| `importlib.import_module("os")` | ✅ **passe** |
| `__import__("os").system("id")` | ✅ **passe** |
| `import http.client` (exfiltration réseau) | ✅ **passe** |
| `open("/tmp/x","w").write(...)` | ✅ **passe** |
| `exec(compile("import os", ...))` | ✅ **passe** |
| `().__class__.__mro__[1].__subclasses__()` | ✅ **passe** |
| `import asyncio` (→ subprocess) | ✅ **passe** |
| `import pickle` | ✅ **passe** |
| `while True: pass` (DoS) | ✅ **passe** |
| `bytearray(10**10)` (bombe mémoire) | ✅ **passe** |

**10 / 10.** `http.client`, `httpx`, `aiohttp`, `importlib`, `builtins`, `pickle`, `io`, `glob`, `tempfile` sont absents de `DANGEROUS_MODULES` alors que `socket` et `urllib` y sont — l'exfiltration réseau est donc triviale.

L'exécution elle-même :

```python
result = subprocess.run([sys.executable, '-S', script_path],
                        cwd=temp_dir, timeout=30, env=env)
```

`-S` saute seulement `site.py`. `cwd=temp_dir` change le répertoire courant, il n'isole pas le système de fichiers. Le script tourne avec **l'UID complet de l'utilisateur**, accès disque total, réseau total. Le retrait de `HTTP_PROXY` ne bloque rien. À la décharge des auteurs, un commentaire dans le code indique que c'est connu :

```python
# Future extension: if getattr(config, 'USE_DOCKER', False): ...
```

**La bonne architecture** : ne jamais faire reposer la sécurité sur une liste blanche d'imports statique. C'est une bataille perdue d'avance contre un générateur de code.

```python
# Isolation réelle, par le noyau — pas par l'AST
docker run --rm \
  --network none \                     # aucun réseau, point
  --read-only --tmpfs /tmp:size=64m \  # FS immuable
  --memory 512m --memory-swap 512m \   # pas de bombe mémoire
  --pids-limit 64 \                    # pas de fork bomb
  --cpus 1.0 \
  --cap-drop ALL --security-opt no-new-privileges \
  --user 65534:65534 \                 # nobody
  -v "$WORK:/work:ro" \
  python:3.12-slim timeout 30 python /work/experiment.py
```

Le filtre AST est alors conservé — mais rétrogradé à ce qu'il est réellement : un **filtre de qualité** (détecter du code manifestement hors-sujet), pas une frontière de sécurité. Le docstring actuel le reconnaît d'ailleurs à demi-mot (« Does NOT try to sandbox execution completely ») ; le problème est que l'appelant, lui, le traite comme une garantie (`if not is_safe: return` puis exécution directe si `is_safe`).

Si Docker n'est pas disponible : `RestrictedPython` + `resource.setrlimit` (RLIMIT_AS, RLIMIT_CPU, RLIMIT_NPROC) + un utilisateur dédié + `unshare -n`. Moins bon, mais d'un ordre de grandeur au-dessus de l'existant.

## 5. Orchestration : le « Supervisor » n'ordonnance rien

### 5.1 Les échecs sont silencieux et l'état se corrompt

```python
try:
    task.result = await action_method(**task.params)
except Exception as e:
    logger.error(f"Task {task.action} on {agent.name} failed: {e}")
    task.result = e          # ← l'exception devient le résultat
# ... et on passe à la tâche suivante
```

Si `run_literature_search` échoue (réseau, arXiv indisponible, quota NCBI), la génération d'hypothèses s'exécute quand même — sans littérature, sans CAG, sans RAG. Elle produira des hypothèses plausibles, hallucinées, non ancrées, qui traverseront ensuite tournoi, expérience et rédaction sans qu'aucune étape ne signale que la base documentaire était vide. **Aucune tâche ne déclare de dépendance ni de politique d'échec.**

### 5.2 `max_iterations` peut abandonner des tâches silencieusement

```python
async def execute_task_queue(self, max_iterations: int = 3):
    for _ in range(max_iterations):
        if not self.task_queue: break
        task = heapq.heappop(self.task_queue)
```

Si la file contient plus de tâches que `max_iterations`, le reste **reste dans la file sans avertissement** et sera exécuté au prochain appel, dans un contexte différent, hors de sa phase. Les appels actuels (`max_iterations=10` pour 4 tâches) ont de la marge, mais c'est de la chance, pas une invariante.

### 5.3 Les priorités encodent un DAG implicite

```python
base_prio = 10 + (iteration * 10)
queue_task(..., "run_review_cycle",     priority=base_prio + 1)
queue_task(..., "run_proximity_cycle",  priority=base_prio + 2)
queue_task(..., "run_tournament_cycle", priority=base_prio + 3)
```

Ces entiers expriment en réalité *review → proximity → tournament → evolution*. Le graphe de dépendances existe, mais dans la tête du développeur, encodé en nombres magiques. Rien n'empêche une refonte future de casser l'ordre.

### 5.4 Aucun parallélisme, alors que tout est déjà `async`

Chaque hypothèse est revue en série (`for hyp in unreviewed: await ...`), chaque match de tournoi est joué en série, chaque expérience aussi. Or ces opérations sont indépendantes. Seul `ReflectionAgent` parallélise (ses 3 reviewers via `asyncio.gather`) — le patron est connu de l'équipe, il n'est simplement pas appliqué au niveau orchestrateur.

### 5.5 Aucun contrôle de budget

Comptage : `ReflectionAgent._review_with_llm` = 1 extraction d'entités + 3 reviewers + 1 méta-reviewer = **5 appels LLM par hypothèse et par revue**. Pour 14 hypothèses : 70 appels rien qu'en revue, auxquels s'ajoutent génération (1 + 1 raffinement × 5), tournoi (12 à 24), évolution (9), préenregistrement, expériences, réplications, rédaction (6 sections + compilation). Un cycle complet dépasse aisément 150 appels. Il n'existe **aucun** garde-fou : pas de budget en tokens, pas de plafond de coût, pas de disjoncteur, pas de `max_tokens`. `utils/llm.py` *compte* les tokens (`_llm_state["total_tokens"]`) mais n'agit jamais dessus.

### 5.6 Correction proposée

```python
@dataclass
class TaskSpec:
    name: str
    action: str
    depends_on: tuple[str, ...] = ()
    on_failure: Literal["abort", "degrade", "retry"] = "abort"
    token_budget: int | None = None

PIPELINE = [
    TaskSpec("literature",  "run_literature_search", on_failure="abort"),
    TaskSpec("scoping",     "run_scoping_cycle",     depends_on=("literature",)),
    TaskSpec("generation",  "run_hypothesis_generation_cycle",
             depends_on=("literature", "scoping")),
    TaskSpec("review",      "run_review_cycle",      depends_on=("generation",)),
    TaskSpec("proximity",   "run_proximity_cycle",   depends_on=("generation",)),  # ∥ review
    TaskSpec("tournament",  "run_tournament_cycle",  depends_on=("review",)),
]
# → topological sort, exécution par vagues avec asyncio.gather,
#   arrêt net si une tâche "abort" échoue, budget vérifié avant chaque vague.
```

Bénéfice double : les échecs deviennent visibles, et `review` ∥ `proximity` (ainsi que toutes les revues entre elles) s'exécutent en parallèle.

## 6. RAG et littérature

### 6.1 Modèle d'embedding inadapté au domaine

```python
self.embedding_model = SentenceTransformer('all-MiniLM-L6-v2')
```

MiniLM est un modèle généraliste 384-d entraîné sur du web. Sur du texte biomédical il confond des entités proches en surface et lointaines en sémantique (nomenclature génique, noms de composés, terminologie de voies de signalisation). Alternatives, par cas d'usage :

- **SPECTER2** — conçu pour la similarité *entre articles* (idéal pour §2.4, la recherche d'antériorité)
- **BioLORD-2023** / **S-PubMedBert-MS-MARCO** — pour la récupération de passages biomédicaux
- Garder MiniLM comme repli si le modèle de domaine n'est pas disponible (le patron de dégradation gracieuse du dépôt s'y prête bien)

### 6.2 Chunking aveugle à la structure de l'article

`SemanticChunker` découpe par paragraphes à 800 tokens sans notion de section. Conséquence : un passage extrait de la **Discussion** (spéculatif, « ces résultats *suggèrent* que… ») est indiscernable, pour tous les agents en aval, d'un passage extrait des **Results** (mesuré). Le `GenerationAgent` ancre donc ses hypothèses sur de la spéculation d'auteur en la traitant comme du fait établi.

Correctif : détecter la section (IMRaD) et l'attacher aux métadonnées du chunk, puis pondérer — Results/Methods > Discussion/Introduction — dans le reranking et dans `Evidence.confidence`.

### 6.3 Corpus biaisé et minuscule

```python
base_query = query + ' AND "free full text"[Filter]'   # literature.py
...
return all_papers[:max_results * 2]                     # → 10 articles par défaut
```

- Le filtre `"free full text"` introduit un **biais de corpus systématique** (sur-représentation de certains éditeurs, journaux et disciplines). Il est compréhensible — le RAG a besoin du texte intégral — mais il doit être explicité et, idéalement, contourné : récupérer les abstracts sans filtre pour l'état de l'art, et le texte intégral seulement pour l'indexation.
- **10 articles** pour fonder un « état de l'art » et une revendication de nouveauté. C'est deux ordres de grandeur en dessous.

### 6.4 Manques structurels

- **Aucune déduplication par DOI** — la dédup se fait sur titre normalisé (`re.sub(r'[^a-zA-Z0-9]','',title.lower())`). Un preprint bioRxiv et sa version publiée, dont le titre diffère d'un mot, comptent double et « corroborent » mutuellement.
- **Aucune détection de rétractation.** Un système qui génère des hypothèses biomédicales doit interroger Retraction Watch / le champ `PublicationStatus` de PubMed. Ancrer une hypothèse sur un article rétracté est un mode de défaillance grave et parfaitement évitable.
- **Aucune provenance chunk → affirmation.** `Evidence.source_ref` est prévu pour ça et n'est jamais rempli. Impossible, aujourd'hui, de répondre à « sur quoi cette affirmation précise repose-t-elle ? ».
- Pas de pondération par date ni par qualité de revue.

## 7. Autres points

**Persistance** — Aucune base de données. Tout est en mémoire dans `ContextMemory`, sérialisé en JSON. `api/server.py` détient une **instance globale unique** de `CoScientist` : pas de multi-session, pas de multi-utilisateur, aucune protection contre les accès concurrents, perte totale de l'état au redémarrage. Les workflows longs (plusieurs minutes) s'exécutent dans le handler HTTP, sans file de jobs ni streaming de progression.

**Reproductibilité** — 30 appels LLM avec des `temperature` codées en dur, aucune graine globale, aucun enregistrement de la version du modèle par appel. Deux exécutions du même objectif de recherche sont incomparables. Pour un système qui prêche le préenregistrement, c'est ironique. Correctif : journaliser `(model, temperature, prompt_hash, response_hash, seed)` pour chaque appel, dans un log d'exécution rejouable.

**Duplication d'interfaces** — `app.py` (Streamlit, 791 l.), `api/server.py` (FastAPI, 426 l.) et `frontend/` (React) réimplémentent chacun l'orchestration des phases. Trois surfaces à maintenir en cohérence. L'API devrait être l'unique point d'entrée, Streamlit et React n'étant que des clients.

**Le README est en retard sur le code** — Il annonce « v2.2 (Avril 2026) » et 6 agents ; le code est en v3.0/v3.1 avec 17 agents, ScopingAgent, ProtocolAgent, WritingAgent, PreregistrationAgent, ReplicationAgent, DevilsAdvocateAgent, un tracker de convergence et un serveur FastAPI. Les instructions d'installation pointent vers `github.com/your-repo/ai-co-scientist.git`.

## 9. Le fil rouge

Ce système est architecturé pour *ressembler* à une démarche scientifique — préenregistrement, peer review, réplication, tournoi, manuscrit — mais plusieurs de ces mécanismes sont, à l'exécution, des coquilles : le hash de préenregistrement ne vérifie rien, la réplication ne réplique rien, la réfutation est un `grep`, la nouveauté est une fonction du mode de génération, et l'expérience est le plus souvent une conversation du modèle avec lui-même.

La bonne nouvelle, et elle est réelle : **les pièces manquantes sont largement déjà écrites**. `Prediction.is_refuted_by` existe. `Claim.evidence_score` existe. `query_hybrid` existe. `falsifiability_score` est calculé. Le travail principal n'est pas d'inventer ces mécanismes, c'est de **les câbler et de les rendre contraignants** — au sens où le système doit pouvoir dire « cette hypothèse est réfutée », « je ne peux pas tester ceci », « ce résultat est une simulation et ne corrobore rien ».

Un co-scientifique qui ne peut pas conclure « non » n'est pas un co-scientifique. C'est un générateur de récits plausibles, et le reste de la machinerie ne fait qu'en augmenter la crédibilité apparente.
